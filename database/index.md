# 인덱스 (Index)

## 내가 공부 전 아는 상식
* 인덱스는 DB 조회를 빠르게 해주는 무언가다.
* 책의 목차와 비슷한 개념인 것 같다.

## 인덱스란
테이블의 특정 컬럼에 대한 검색 속도를 높이기 위한 자료구조.
인덱스 없이 조회하면 테이블 전체를 스캔(Full Table Scan)한다.
인덱스가 있으면 해당 컬럼의 정렬된 사본을 통해 빠르게 찾는다.

## B-Tree 인덱스 (기본)
MySQL의 기본 인덱스 구조. 정렬된 트리 형태로 저장해 O(log n) 탐색.

```
      [50]
     /    \
  [20]    [80]
  /  \    /  \
[10][30][60][90]
```

## 언제 인덱스를 쓰는가

| 상황 | 인덱스 효과 |
|---|---|
| WHERE 조건으로 자주 조회되는 컬럼 | 빠른 탐색 |
| JOIN에서 연결 키로 쓰이는 컬럼 | 빠른 연결 |
| ORDER BY, GROUP BY 대상 컬럼 | 정렬 생략 가능 |
| 중복이 많은 컬럼 (성별 등) | 효과 거의 없음 |

## 인덱스의 단점
- **쓰기 성능 저하:** INSERT/UPDATE/DELETE 시 인덱스도 같이 갱신 → 느려짐
- **저장 공간 추가 사용:** 인덱스 자체도 디스크를 차지
- **무조건 인덱스가 답이 아님** → 쓰기가 많은 테이블엔 신중하게 적용

## 복합 인덱스
여러 컬럼을 묶어 인덱스 생성. **순서가 중요하다.**

```sql
CREATE INDEX idx_user ON orders (user_id, created_at);
-- user_id 단독 조회 → 사용 가능
-- user_id + created_at 조회 → 사용 가능
-- created_at 단독 조회 → 사용 불가 (선두 컬럼이 없음)
```

## 면접 한 줄 답변
> "인덱스는 조회 성능을 높이기 위해 특정 컬럼에 B-Tree 구조의 정렬된 사본을 만드는 것입니다. 조회는 빨라지지만 쓰기 성능과 저장 공간에 트레이드오프가 있어서, 자주 조회되는 컬럼에만 선택적으로 적용합니다."

## 프로젝트 적용
- 팡팡팡: user_id, created_at으로 진단 이력 조회 → 복합 인덱스 적용 고려
- 애완용품샵: 상품 카테고리·가격 필터 조회 → WHERE 대상 컬럼에 인덱스 필요
